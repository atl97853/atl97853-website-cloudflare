# CSS Refactor Workflow

This document describes the practical workflow used during the CSS refactor.

The goal is to keep refactors small, mechanical, and safe. For the current pass, the priority is not to redesign the system. The priority is to remove unused classes, remove unnecessary `Card.astro` overrides, and replace safe hardcoded values with existing tokens.

---

## 1. Current refactor goal

```text
1. Remove unused CSS classes.
2. Remove classes that duplicate Card.astro/card.css behavior.
3. Use hook classes only when needed.
4. Replace hardcoded CSS values with existing tokens when the match is clear.
5. Do not create new tokens unless the value is reusable across components.
6. Preserve the current visual result.
```

This pass should stay simple. Do not reorganize the entire token system yet. That can be a later refactor.

---

## 2. Recommended order

Work one file at a time.

```text
1. Pick one component/page.
2. Inspect the Card.astro usage.
3. Inspect the HTML classes.
4. Compare the CSS selectors against the HTML.
5. Remove selectors for classes that no longer exist.
6. Remove Card wrapper/body/title classes that do not add real behavior.
7. Decide whether a hook class is needed.
8. Replace safe hardcoded values with existing tokens.
9. Test dark, light, and experimental themes.
10. Commit that file or small group of related files.
```

Small commits make it easier to debug visual regressions.

---

## 3. First question: does this component use Card.astro?

If yes, look for:

```astro
<Card
    class="..."
    bodyClass="..."
    title="..."
    titleId="..."
>
```

Then ask:

```text
Does class="..." style the outer Card for a real reason?
Does bodyClass="..." style the generated Card body for a real reason?
Is the title now rendered by Card.astro instead of the component?
Are old title classes still left in CSS?
```

---

## 4. Card-owned classes

`Card.astro` owns these classes:

```css
.c-card
.c-card__header
.c-card__body
```

`card.css` styles them globally.

Do not duplicate them inside individual components unless the component needs a real override.

Remove old classes like:

```css
.c-posts-card__title
.c-logs-card__title
.c-blog-post__body
.c-coursework-card__body
```

when they are unused or when their styles can move to local content wrappers.

---

## 5. Decide whether a hook class is needed

Use this decision tree:

```text
Do you need to style markup generated by Card.astro?
  No  -> Use a local wrapper or local content class.
  Yes -> Continue.

Can you style your own wrapper inside the Card instead?
  Yes -> Use the wrapper. No hook needed.
  No  -> Use a hook class through class/bodyClass.

Is the hook class specific to this component?
  No  -> Rename it.
  Yes -> Use :global(.hook-class) and document it.
```

---

## 6. Preferred pattern: local wrapper

Use this when the component can own the markup.

```astro
<Card title="Coursework">
    <div class="c-coursework">
        ...
    </div>
</Card>
```

```css
.c-coursework {
    max-width: 48rem;
    line-height: var(--lh-body);
}
```

Good for:

- text width
- local typography
- content-specific spacing
- prose styling
- list styling
- empty states

---

## 7. Hook pattern: generated Card body

Use this when the generated `.c-card__body` itself must change.

```astro
<Card bodyClass="c-library-book__body">
    ...
</Card>
```

```css
:global(.c-library-book__body) {
    display: grid;
    grid-template-columns: 120px minmax(0, 1fr);
}
```

Good for:

- changing Card body display to `grid`
- changing Card body display to `flex`
- aligning direct slot children through the generated body
- adding a modifier to the generated body

---

## 8. Hardcoded value replacement rule

Replace hardcoded values only when a matching token already exists and clearly means the same thing.

Good replacements:

```css
margin: 0;
padding: 0;
```

to:

```css
margin: var(--space-none);
padding: var(--space-none);
```

```css
font-weight: 700;
```

to:

```css
font-weight: var(--fw-bold);
```

```css
line-height: 1.5;
```

to:

```css
line-height: var(--lh-text);
```

```css
line-height: 1.4;
```

to:

```css
line-height: var(--lh-link);
```

only if `--lh-link` already exists and this is actually link-like or compact text.

---

## 9. Values to leave hardcoded for now

Leave unique component values hardcoded unless a matching token already exists.

Examples:

```css
max-width: 48rem;
max-width: min(100%, 74ch);
grid-template-columns: 120px minmax(0, 1fr);
line-height: 1.72;
line-height: 1.35;
letter-spacing: 0.03em;
text-underline-offset: 0.14em;
padding: 0.1rem 0.45rem;
padding-left: 1.35rem;
margin-top: 0.4rem;
```

These may become tokens later, but not during this simple cleanup pass.

---

## 10. When to add a new token

Add a new token only if the value is clearly reusable across multiple files or components.

Good token candidates:

```css
--space-none
--fw-bold
--lh-body
--lh-text
--lh-heading
--lh-link
--list-padding-inline
```

Poor token candidates:

```css
--coursework-list-indent
--blog-post-title-line-height
--library-book-cover-width
--logs-empty-margin
```

Those are component-specific.

If a component-specific value is repeated within the same component, use a local CSS variable later. Do not put it in `tokens.css` unless it becomes reusable.

---

## 11. Removing unused classes

Process:

```text
1. List all classes used in the HTML.
2. List all selectors in the style block.
3. Delete selectors that do not match the HTML.
4. Delete selectors that were only for old Card markup.
5. Check if Card.astro now renders the title/header internally.
```

Example:

```css
.c-posts-card__title {
    ...
}
```

Remove it if the component now renders:

```astro
<Card title="Posts">
```

because the title is now:

```html
<h2 class="c-card__header">
```

---

## 12. Removing unnecessary Card body overrides

Bad when unnecessary:

```astro
<Card bodyClass="c-blog-post__body">
    <div class="c-blog-post__content">
        ...
    </div>
</Card>
```

```css
.c-blog-post__body {
    line-height: 1.72;
}
```

Better:

```astro
<Card class="c-blog-post">
    <div class="c-blog-post__content">
        ...
    </div>
</Card>
```

```css
.c-blog-post__content {
    line-height: 1.72;
}
```

The typography belongs to the content wrapper, not the generated Card body.

## 14. Testing checklist

After each file refactor:

```text
[ ] Page still builds.
[ ] No obvious layout shift in dark theme.
[ ] No obvious layout shift in light theme.
[ ] Experimental theme can differ if expected.
[ ] Card spacing still looks correct.
[ ] Titles still render.
[ ] Custom header links still work.
[ ] Empty states still render.
[ ] Responsive behavior still works.
[ ] No selectors point to removed classes.
```

---

## 15. Commit strategy

Commit small groups of related changes.

Good commit scopes:

```text
refactor(pfp): ...
refactor(logs): ...
refactor(library): ...
refactor(coursework): ...
refactor(blog): ...
docs(css): ...
```

Commit subject examples:

```bash
git commit -m "refactor(logs): use tokens, remove body hook"
```

```bash
git commit -m "refactor(library): use hook and tokens"
```

```bash
git commit -m "refactor(blog): remove card body hook"
```

Add a body when the change explains architecture:

```bash
git commit -m "refactor(pfp): add card body hook class" -m "Pass a component-specific hook class through Card's bodyClass prop so Pfp.astro can style the generated Card body without modifying Card.astro or affecting other Card instances."
```

## 16. Documentation workflow

When documentation needs updating:

```text
1. Update css-architecture.md if a file responsibility changed.
2. Update reusable-components.md if Card.astro or LinkList.astro behavior changed.
3. Update hook-classes.md if a new hook pattern is introduced.
4. Update css-refactor-workflow.md if the refactor process changes.
```

Do not mix major documentation rewrites into small component refactor commits unless the code change depends on the documentation.

---

## 17. Final rule

```text
Do the smallest safe refactor first.
Do not create a new abstraction until the duplication is clear.
Do not use a hook class when a local wrapper is enough.
Do not create a token when an existing token or a hardcoded local value is clearer.
```
